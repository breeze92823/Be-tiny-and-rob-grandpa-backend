# Tiny Thieves: Grandpa's House — BACKEND (game server)

Frontend (3D client) lives at `../Be-tiny-and-rob-grandpa` (client side of the protocol: its `src/net.js`; the contract is its `GAME_DESIGN.md`, section "Multiplayer protocol", and this file). Colyseus + Mongo, ported from `C:\ThreeJS\Risky-heist\Risky-heist-backend` and reshaped for the co-op heist: a lobby with 3 crew pads, and a relay for the heists they launch.

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`, Bloxity faked via `__setVerifierForTest` / `__setFetchForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { token, username, pfp, pose?, avatar? })`). Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`) and relays the heist; no gameplay rules live here. `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable. `/health` for Legion; `/monitor` and the playground are dev-only.
- **Identity (Bloxity audit rule)**: the server never trusts an id from the client. `onAuth` sends the join option `token` (`Legion.SDK.auth.getToken()`) to `POST {BLOXITY_API_URL}/v1/auth/game-token/verify` (`Authorization: Bearer <token>`, body `{ gameSlug: "be-tiny-and-rob-grandpa" }`) and uses only the returned `user._id` (`src/bloxity.ts` `verifyToken`); a refused / missing token (or an unreachable Bloxity) is a guest, who is never loaded or saved. Display names of verified players come from Bloxity. `identify` re-verifies a new `token` after a mid-session sign-in / sign-out ("" = signed out); an id in a message is ignored. Tests: token `tok-<id>` = account `<id>` (`test/server.ts` `fakeVerify`; `test/Bloxity.test.ts`).
- **Bloxity reporters** (`src/bloxity.ts`, started by `installReporters()` in `src/index.ts`; each is a no-op unless the hosting variables are set): live rooms every 2 s (`POST {MATCHMAKER_REPORT_URL}/{BLOXITY_GAME_ID}/rooms`, `matchMaker.query`), game stats every 60 s and on SIGTERM (`POST {BLOXITY_API_URL}/v1/games/{BLOXITY_GAME_ID}/stats`, definitions in `STAT_DEFINITIONS`: escapes, coins_earned, best_haul, loot_stolen, heists, times_caught, jobs_done; values clamped to Boxity's per-type ceilings), hosted leaderboards every 30 s, changed scores only (`POST .../v1/leaderboards/hosted/{gameId}/report`, boards in `LEADERBOARD_BOARDS`: `escapes`, `earned`, `besthaul`, `stolen`). All read the server's own copy of each signed-in player's progress (never a client packet), report `legion_<id>` users, skip guests, use `Authorization: Bearer $BLOXITY_REPORT_TOKEN`. Env: `BLOXITY_API_URL` (default prod, only when missing), `BLOXITY_GAME_ID`, `BLOXITY_REPORT_TOKEN`, `MATCHMAKER_REPORT_URL`, `POD_NAME`/`HOSTNAME` (see `.env.example`).
- **Private rooms (Play with friends)**: a client that creates the room with the option `private: true` (`?instantMultiplayer=true`) gets a room that `setPrivate(true)` keeps out of strangers' `joinOrCreate`; it is reachable by room id only (the invite link), `autoDispose` is off, and when empty it lives `PRIVATE_KEEPALIVE_MS` (30 s) so a reconnect can return, then disposes (`test/PrivateRoom.test.ts`). The avatar JSON the server relays is never parsed, so `characterId` (custom characters) travels with the other equipped ids.
- **Rewarded ads**: message `adReward` { token, placement } -> the server checks the token with `POST {BLOXITY_API_URL}/v1/ads/reward/verify` { gameSlug, rewardToken } and answers `adRewardResult` { ok, placement }; the client grants the reward only on `ok`.
- **Currency rule** (root `CLAUDE.md`): nothing is ever bought with Gems/Robux. The save has only `coins` (earned by escaping); the server sells nothing and has no premium-currency field.
- The Mongo doc is the signed-in player's save. The client writes no local copy (nothing in `localStorage`); on join the server's save replaces the fresh state, and a new account (`noProgress`) saves the state played so far as its first save. A guest's (or a serverless session's) progress is not kept past the page load.
- Messages client -> server (saves / identity): `saveProgress` (the whole snapshot, throttled client-side, plus a flush when the tab hides/closes), `identify` (`{ token, username, pfp }` after a sign-in/out mid-session; without `token` it only refreshes name/picture), `adReward`. Server -> client (private): `progress` (the saved doc, sanitized, + `serverTime`), `noProgress` ({ serverTime }: new account, guest, or no database: the client keeps its state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten), `leaderboard`, `adRewardResult`. `serverTime` lets the client turn pad `startsAt` (server epoch ms) into a local countdown. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted (closed with code 4000, `CloseCode.CONSENTED`). A dropped connection may reconnect for `RECONNECT_SECONDS` (20) via `allowReconnection`.
- Saved progress shape (`PlayerDoc` in `src/db.ts`, bounds in `src/constants.ts`): `coins` (0..1e12), `upgrades { arms, grip, lungs, feet, soft, ninja }` (whole 0..5; when sent, every track is stored, a missing one as 0), `gadgets { id: count }` (ids in `GADGET_IDS`: marbles, glue, banana, alarm, smoke, sleep, xray, energy, bazooka; whole 0..99; unknown ids dropped), `stats { heists, escapes, caught, stolen, earned, bestHaul, jobs }` (non-negative, <= 1e12, the counters heists/escapes/caught/jobs whole), `tutorialDone` (bool), `prefs { music, sfx, lights }` (bools, on unless `false`), `lastSeen` (epoch ms; the server also stamps it when a player really leaves). Fields a save leaves out are kept as stored. **Stats never go down**: `saveProgress` writes them with `$max` on `stats.<key>` (never `$set`), so a stale or forged lower value changes nothing; the server's in-memory copy merges the same way (`maxStats`).
- Leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): top `LEADERBOARD_SIZE` saved players by each of `LEADERBOARD_STATS` (`escapes`, `earned`, `bestHaul`, `stolen`; doc paths in `LEADERBOARD_FIELDS`, all under `stats.`), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { escapes|earned|bestHaul|stolen: [{ name, value }] }, ranks: { stat: n | null } }, sent after each load and to everyone every `LEADERBOARD_EVERY_MS`. `connectDb` creates a descending index per stat. (Hosted board ids are lowercase: `besthaul`. The client declares the same boards with the same ids and labels in its `config.js` `LEADERBOARDS`; change both together.)
- **Room size**: `ROOM_MAX_CLIENTS` = 12 (one lobby, 3 pads x 4 players). A 13th player is refused and the Bloxity matchmaker opens another room.
- **State** (`src/rooms/schema/WorldState.ts`): `WorldState { players: MapSchema<PlayerState>, pads: ArraySchema<PadState> }`, exactly 3 pads created in `onCreate`. `PlayerState`: `username`, `signedIn`, `pfp`, `userId`, `avatar`, `emote`, pose `x y z yaw speed grounded crouch grab gx gy gz held out` (client-set through `pose`), and server-set only: `zone` ("lobby", or "h0".."h2" while in that pad's heist; clients draw only the players in their own zone) and `escapes` (this session's escapes). `PadState`: `index`, `difficulty` (pads 0..2 = all normal), `members` (session ids waiting, max `PAD_SIZE` 4), `startsAt` (server epoch ms, 0 = idle), `running`, `crew` (session ids in the heist), `host` (session id running Grandpa + physics), `seed` (uint32), `money` (crew bank), `target` (1000 for normal; set from the start), `heistId`.
- **Crew pads** (`src/pads.ts`, `test/Pads.test.ts`): `joinPad` { pad } only from zone "lobby", onto an existing, idle (not running) pad with < 4 members; moves the sender off any other pad. A refused join gets no reply: the client reads `state.pads` (`members`, `running`) to see whether it was seated and asks again (at most once a second) while it stands on the pad. The first member sets `startsAt = now + PAD_COUNTDOWN_MS` (20 s); reaching 4 sets `startsAt = min(startsAt, now + PAD_FULL_COUNTDOWN_MS)` (5 s). `leavePad` takes the sender off every pad; an emptied pad goes back to `startsAt = 0`. Leaving the room, or dropping (even while allowed to reconnect), also frees the seat, so a dropped player is never launched. The room clock (`PAD_TICK_MS` 250 ms) calls `tickPads(Date.now())`: every idle pad with members and `startsAt <= now` launches: `running = true`, `crew` = members (in join order), members cleared, `startsAt = 0`, `host = crew[0]`, fresh random `seed` and `heistId` (8 chars), `money = 0`, `target` by difficulty; each crew player gets `zone = "h<index>"`, `held = out = false` and the private message `heistStart` { pad, heistId, seed, difficulty, target, host, crew }.
- **Heist relay** (all ignored unless the sender is in a running pad's crew; payloads are opaque plain objects, never parsed, dropped when not an object or when their JSON is over the cap): `hs` (host snapshot, <= 24 KB, `HS_MAX_BYTES`) and `hb` (host event, <= 8 KB) only from that pad's `host`, sent as-is to every OTHER crew member (never echoed to the sender, never to the lobby); `ha` (crew action, <= 4 KB) from a non-host crew member, sent to the host only as `{ ...payload, from: senderSessionId }` (a client-sent `from` is overwritten; the host's own `ha` is ignored). `steal` { value } from the host only: `money += clamp(round(value), 0, STEAL_MAX = 2000)` (non-numbers ignored). `escaped` (out through the van: `escapes += 1`) and `leaveHeist` take the sender out of the crew: `zone = "lobby"`, `held = out = false`. Leaving the room takes them out too, but only once the reconnection window has closed (a dropped host keeps hosting meanwhile). Whenever someone leaves a crew: if they hosted and crew remains, `host` = the next crew member and the remaining crew gets `hostChanged` { pad, host }; when the crew is empty the pad resets (`running = false`, crew cleared, `host = ""`, `money = 0`, `heistId = ""`) and the whole room gets `heistOver` { pad }. Tests drive the pad clock with `room.tickPads(now)` or shorten the countdowns with `__setPadTimingForTest`.
- Presence (`src/presence.ts`, `test/Presence.test.ts`): relayed through the roster as sent, only bounded. `pose` { x, y, z, yaw, speed, grounded, crouch, grab, gx, gy, gz, held, out } (every field optional, malformed ones ignored): |x|, |z|, |gx|, |gz| <= `POSE_BOUNDS.xz` (3000), y / gy in -50..400, `yaw` wrapped to -PI..PI, `speed` 0..500 m/s, the rest booleans; `zone` / `escapes` can never be set this way. `setAvatar` { avatar } (Bloxity look JSON, at most `AVATAR_MAX_LEN`, never parsed: clients must sanitize ids before use), `emote` { id } (`ID_PATTERN` or "" = stop). The join options may carry `pose` and `avatar` too. `userId` is public on purpose (Boxity chat messages carry it, so a bubble finds its character).
- `src/constants.ts` bounds must cover the client's `src/config.js` (upgrade / gadget ids and caps, pad count / size / difficulties / targets, countdowns, world coordinates: house at the origin, lobby at z 1500). A contract change goes in both projects (and `test/Sanitize.test.ts` / `test/Pads.test.ts`).
- Local end-to-end: run this server (`npm start`, no Mongo = `noProgress` for everyone) and the client with `npm run dev` (it defaults to `ws://localhost:2567`). Locally the player is a guest (no Bloxity token, nothing saved) unless the real SDK signs them in; the server tests are the way to exercise saves. Two browser tabs on the same pad exercise the heist relay.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image (`Dockerfile`) and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending BOTH `roomSize` and `seatCap` = `ROOM_MAX_CLIENTS` (12) read from `src/constants.ts`. The two Boxity docs differ: the SDK docs (https://docs.bloxity.io, "Multiplayer connection") say `maxClients` = the room size (2-100), send `roomSize`, never `seatCap`; the hosting docs (https://hosting.bloxity.io/docs) document `seatCap` (= `maxClients`, default 50). Both carry the same value, so the matchmaker fills a pod to one room whichever it reads. A full room makes the matchmaker open another. Needs repo var/secret `LEGION_GAME_ID` (= `be-tiny-and-rob-grandpa`, also the workflow's fallback) and secret `LEGION_DEPLOY_TOKEN`.
